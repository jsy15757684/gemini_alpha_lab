# 🪙 빗썸 원화 자동매매 콘솔

빗썸 원화마켓 4종(BTC · ETH · SOL · XRP)의 시세 조회, 전략 백테스트,
자동매매 봇. **그 외 기능은 없습니다.**

---

## 설계 원칙

이 프로그램은 이전 버전에서 확인된 문제들을 구조적으로 막도록 다시 만들었습니다.

**1. 봇과 백테스트가 같은 판단 코드를 씁니다**
`services/strategy.py` 의 `decide()` 하나만 존재하고, 실시간 봇과 백테스트가
모두 이것을 호출합니다. 백테스트 결과가 실제 봇의 행동과 일치합니다.

**2. 못 받은 값은 만들지 않습니다**
시세나 캔들을 받지 못하면 추정치를 채우지 않고 그 틱의 판단을 보류합니다.
실시세가 없으면 봇 가동 자체가 거부됩니다.

**3. 주문이 실패하면 내부 장부도 바꾸지 않습니다**
실주문이 거부되면 포지션을 그대로 둡니다. 내부 기록과 거래소 실제 보유량이
어긋나는 것이 가장 위험합니다.

**4. 모든 판단에 근거가 남습니다**
진입·청산마다 어떤 규칙이 왜 발동했는지 로그와 화면에 표시됩니다.

**5. 성과 수치를 지어내지 않습니다**
화면의 모든 숫자는 실제 조회·계산 결과입니다. 홍보용 고정 수치는 없습니다.

## 전략

단순하고 추적 가능한 규칙만 씁니다.

| 구분 | 조건 |
| :--- | :--- |
| **진입** | RSI 가 매수 기준선(기본 35)을 **아래에서 위로** 통과 |
| **청산** | 익절(+4%) / 손절(-2%) / RSI 과매수(70) / 트레일링 스톱(선택) |

RSI 하향 돌파가 아니라 **상향 돌파**로 진입합니다. 하락 중 매수를 피하고
반등을 확인한 뒤 들어갑니다.

> **추세 필터는 기본으로 꺼져 있습니다.** RSI 과매도 반등은 정의상 가격이
> 이동평균 아래일 때 발생하므로, '종가 > 장기MA' 를 함께 요구하면 두 조건이
> 배타적이 되어 진입 신호가 사라집니다. 실측 결과 5종목 × 2간격에서
> 필터 없음 35회 진입 → 필터 적용 시 0~1회였습니다.

## 실행

```bash
git clone https://github.com/jsy15757684/gemini_alpha_lab.git
cd gemini_alpha_lab
cp .env.example .env      # APP_ACCESS_PASSWORD 를 채웁니다
./run.sh
```

`run.sh` 가 가상환경 생성 · 의존성 설치 · `.env` 로드 · 포트 정리까지 처리합니다.
접속은 `http://localhost:8888`.

`APP_ACCESS_PASSWORD` 가 없으면 서버는 뜨지만 **모든 데이터 API 가 503 으로
잠깁니다.** 열린 상태로 떨어지지 않게 의도한 동작입니다.

`.env` 를 수정한 뒤에는 **반드시 서버를 재시작**해야 반영됩니다.

### 환경변수

전체 목록은 [.env.example](.env.example) 참고.

| 변수 | 필수 | 설명 |
| :--- | :--- | :--- |
| `APP_ACCESS_PASSWORD` | ✅ | 접속 비밀번호. 없으면 전체 잠금 |
| `BITHUMB_API_KEY` / `BITHUMB_SECRET_KEY` | | 실계좌 연동. 환경변수로 넣으면 재시작에도 유지 |
| `BITHUMB_PROXY_URL` | | 고정 IP 프록시 경유 (아웃바운드 IP 등록 불가 환경) |

숫자를 남겨둡니다.

**USDT 환차익** — 차익거래가 아니라 환투자입니다.
137일 실측에서 프리미엄 변동폭은 5.23%p, 환율 변동폭은 16.29% 였습니다.
어떤 매수/매도선 조합으로도 총손익이 음수였고(-0.8%→+1.0%: 왕복 2회 -7.15%),
최악의 거래는 프리미엄이 목표대로 +2.80%p 개선됐는데 환율이 -10.50% 빠져
-7.95% 손실이었습니다. 프리미엄이 +2% 를 넘은 날은 0일이라 기본 매도선으로는
청산되지 않습니다.

주말에는 신호를 쓰지 않습니다. 서울외환시장은 주 5일만 열려서(공시 240일
전부 월~금, 토·일 0건) 토·일에는 금요일 값이 그대로 남는데, 빗썸 USDT 는

생기는 착시입니다 — 24개 주말을 금 종가→월 종가로 대조하면 USDT -0.242%,
공시환율 -0.222% 로 **프리미엄 자체는 -0.020%p 밖에 안 변합니다.** USDT 가
아직 공시되지 않은 환율 움직임을 먼저 반영하고 있을 뿐입니다. 그 착시를
신호로 받아 매수선(-0.8%)을 통과한 17회를 따라 샀다면 다음 영업일 평균
-0.254% · 승률 12.5% 였고, 일요일 프리미엄의 부호가 월요일 환율 방향을
맞춘 비율은 46% 로 예측력이 없었습니다.
그래서 환율 기준일이 오늘이 아니면 **진입도 익절도 하지 않습니다.**
가격 기준 손절만 계속 작동합니다 — 실제 손실은 공시와 무관하게 쌓입니다.
같은 규칙을 차익거래 탭의 `usdt_swap` 시뮬레이터에도 적용했습니다. 두 구현이
같은 현상을 다르게 다루면 어느 쪽 숫자를 믿어야 하는지 알 수 없어집니다.
무전송 양방향(`spatial_dual`)은 빗썸÷바이낸스 가격비만 보고 환율을 쓰지
않으므로 이 게이트를 걸지 않습니다.
화면에도 `⏸ 기준 2026-09-18 (1일 전) · 외환시장 휴장` 으로 표시됩니다.

참고로 주말 보유 자체가 불리했습니다: 금→월 28회 중 23회 손실(승률 17.9%,
평균 -0.261%). 1년치 공시환율에서도 금→월 변화는 평균 -0.199%(n=44,
t=-2.47)로 유의한 반면 평일은 +0.040%(t=+0.87)로 무의미했습니다. 다만
구간을 쪼개면 -0.228% → -0.286% → -0.094% 로 최근에 약해지고 있어, 이걸
근거로 '주말 청산' 규칙을 넣지는 않았습니다. 요일 효과는 잘 깨집니다.

**무한매수 목표 익절률** — 합계로 보면 높을수록 좋지만, 국면을 쪼개면 다릅니다.
112구간 × 목표 6종 실측입니다.

| 목표 | 수익률 | 최대낙폭 | 익절 체결 | 쿼터방어 | 승률 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 5% | -0.62% | 5.27% | 1.60회 | 0.46 | 73.0% |

목표를 올리면 **익절이 실제로 체결된 횟수가 1.60 → 0.27회로 줄고**, 회차를 다
소진해 쿼터방어로 넘어가는 빈도가 0.46 → 0.83 으로 늘고, 낙폭도 커집니다.

**10%가 최고(+1.97%)이고 15%는 +0.45%로 떨어집니다** — 단조가 아닙니다.
15% 의 이득은 급등장(+10% 이상)에만 있습니다. 그래서 **기본 10% 를 두고
AI 가 과열을 감지할 때만 13.5~15% 로 올리는 현재 방식이 측정과 맞습니다.**
기본값을 15% 로 고정하는 것은 권하지 않습니다.

**캔들 간격** — 최적값이 아니라 '자본을 며칠에 걸쳐 넣을지' 를 정하는 값입니다.
회차 매수는 새 봉이 뜰 때마다 한 번이므로 `40분할 × 간격` 이 자본 소진 시간입니다
(1시간봉 1.7일 · 6시간봉 10일 · 24시간봉 40일). 같은 달력 창으로 비교하면
(지표는 각 간격의 전체 히스토리로 예열):

| 창 | 간격 | 수익률 | 벤치 | 알파 | 낙폭 | 쿼터방어 |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: |
| 최근 8일 | 6h | +4.11% | +6.75% | -2.64% | 1.89% | 0 |
| | 12h | +1.62% | +6.61% | -4.99% | 0.43% | 0 |
| | 24h | +0.95% | +7.51% | -6.56% | 0.32% | 0 |

짧은 간격이 수익률과 낙폭을 함께 올립니다(자본을 빨리 넣으니까). 40일 창에서
6시간봉은 회차를 소진해 **쿼터방어를 6.75회** 쳤고 24시간봉은 0회였습니다.
1~4시간봉은 히스토리가 200봉뿐이라 예열분이 없어 비교 자체가 불가능했습니다 —
1시간봉은 40회차를 1.7일에 소진해 사실상 일시불 매수가 되므로, 분할의 전제가
사라집니다.

**무한매수 추세 조절** — 공짜 개선이 아니라 국면에 거는 방향 베팅입니다. 기본값 off.
파라미터 192조합을 학습 60% / 검증 40% 로 나눠 재보니 검증에서 단순보유를 이긴
조합이 6/192(3%) 였고, 학습 1등을 고르면 오히려 평균보다 나빴습니다(검증 알파
-10.95%p vs 전체 -10.15%p). 즉 과거 최적값 찾기는 작동하지 않습니다.
국면별로 보면 원인이 분명합니다 — 급락장 24구간에서 알파 +8.79%p(96% 승),
급등장 39구간에서 **-17.06%p(0% 승)**, 알파와 벤치마크의 상관계수 -0.939.
**이 전략은 수익을 키우는 도구가 아니라 낙폭을 줄이는 도구입니다.**

그래서 추세 조절의 문턱은 재서 고르지 않고 통상적 정의를 그대로 씁니다
(상승 = 종가 > 30봉 평균 && 평균선 상승). 검증 구간 288조합 실측:

| 모드 | 수익률 | 최대낙폭 | 급등장 | 급락장 |
| :--- | ---: | ---: | ---: | ---: |
| `off` (기본) | +6.82% | 5.54% | — | — |
| `boost_up` | +8.60% | 7.24% | +2.07%p | **-2.39%p** |
| `pause_down` | +4.97% | 4.76% | — | — |

`boost_up` 은 수익률 +1.78%p 를 벌면서 낙폭도 +1.70%p 늘립니다(조합의 77%에서
수익률 개선). 급락장 낙폭은 14.78% → 17.74% 로 커집니다. 측정 구간이 상승장에
치우쳐(112구간 중 급등 39·급락 24) 합계가 플러스로 나온 것이라, **하락장이 길면
부호가 뒤집힙니다.** `pause_down` 은 수익률을 -1.85%p 깎았고 벤치마크를 이긴
조합이 0% 였습니다(낙폭만 -0.77%p 줄었습니다).

측정의 한계도 적어둡니다. 빗썸 공개 API 가 간격과 무관하게 **200봉**이라
일봉 200일·6시간봉 50일이 전부이고, **AI 동적 조절은 과거 재현이 안 돼
백테스트에 넣지 못했습니다**(위 숫자는 전부 AI 끈 기준선입니다).

**무전송 양방향** — 아직 시뮬레이터입니다. 만들지 말지 판단할 데이터를 먼저 모읍니다.

서버가 1분마다 빗썸·바이낸스 **최우선 호가**를 읽어 `data/spread_log.csv`
에 쌓습니다(주문 없음, 공개 API만). 레이더가 보여주는 체결가 기준 괴리는

**김프 델타뉴트럴** — 제거했습니다 (2026-09-18). 아래가 그 근거입니다.

## 실전 매매 전 확인

- **빗썸은 API 키에 IP 등록이 필수입니다.** `빗썸 계정` 탭에 등록할 IP 가 표시됩니다.
- **유동 IP 회선(집·사무실)은 운영에 부적합합니다.** IP 가 바뀌면 인증이 끊깁니다.
  24시간 운영은 고정 IP 환경에서 하세요.
- **먼저 백테스트, 다음 모의투자, 마지막에 실전** 순서로 확인하세요.
  모의투자(PAPER)는 주문을 내지 않고 같은 전략으로 동작합니다.
- **실전 가동 전 서버가 잔고를 확인합니다.** 인증 실패나 잔고 부족이면 가동을 거부합니다.
- 백테스트는 신호 캔들의 종가 체결·수수료 반영·**슬리피지 미반영** 가정입니다.
  실전 성과는 이보다 나쁠 수 있습니다.

조작한 시장을 주입해 각 분기를 강제로 통과시킵니다. 판단 로직을 테스트가
재구현하지 않고 **실제 봇 루프를 돌립니다** — 재구현하면 '작성자의 이해' 를
검증할 뿐 배포된 코드를 검증하지 못합니다. 실제로 이 방식으로 손절-재매수

저장 경로는 임시 디렉터리로 갈아끼워 실행하므로 `data/` 를 건드리지 않습니다.

### 화면을 눈으로 확인할 때

```bash
python3 scripts/ui_preview.py          # 포트 8890 에 격리 실행
python3 scripts/ui_preview.py --check  # 차단만 검증하고 종료
```

개발 기계에서 UI 를 보려고 서버를 그냥 띄우면 **실계좌 키가 딸려 들어갑니다.**
`os.environ.pop()` 으로 지워도 소용없습니다 — `server.py` 가 import 시점에
`.env` 를 다시 읽고, `gemini_service.py` 에는 그와 별개로 `.env` 를 직접 읽는
두 번째 경로가 있습니다. 실제로 그렇게 빗썸 인증 호출이 나갔고(IP 화이트리스트가
막았습니다) Gemini 는 IP 제한이 없어 호출이 그대로 나가 할당량을 썼습니다.

그래서 이 스크립트는 네 겹으로 막습니다. 어느 하나가 뚫려도 나머지가 남습니다.

1. `APP_SKIP_DOTENV=1` — `server.py` 와 `gemini_service.py` 둘 다 `.env` 를 읽지 않음
2. 환경변수에서 키 제거 (셸에 남아 있던 것 포함)
3. **사전 점검 후 기동** — 그래도 키가 남아 있으면 서버를 띄우지 않음
4. 빗썸 인증 메서드 6종과 Gemini 호출 3종을 예외로 교체 — 키가 들어와도 요청이 못 나감

데이터 경로도 임시 디렉터리로 돌려 운영·개발 장부를 건드리지 않습니다.
화면에서는 `빗썸 미연동`, AI 분석은 오류로 보이는데 의도된 동작입니다.

검증은 `python3 test_preview_isolation.py` (9개 항목). 사고를 그대로 재현해
**차단이 뚫렸을 때 기동이 멈추는지**까지 확인합니다.

### 체결 일지 상한

`data/trades.json` 은 최대 **50,000행**(약 20MB)입니다. 실측으로 행당
415바이트, 봇 2개에 하루 43.8행이라 3년치입니다. 디스크 여유가 14GB 이라
용량 때문에 낮게 잡을 이유가 없습니다 — 예전 상한 5,000행은 3.4개월이면
닿았고, 봇 10개면 3주면 닿았습니다.

상한을 넘으면 **오래된 매수 행부터 버리고 매도 행은 남깁니다.** 매도만
실현손익을 나르기 때문입니다(전체의 5% 남짓). 매도를 함께 버리면 화면의
'누적 실현손익' 이 조용히 줄어드는데, 이 파일을 봇 상태와 분리한 이유가
바로 그것을 막는 것이었습니다. 매도만으로 상한을 넘는 경우(봇 10개로
5년 남짓)에는 어쩔 수 없이 오래된 것부터 버리되 경고를 남깁니다.

참고로 AI 판단 사유가 실제로 용량을 먹는 곳은 일지가 아니라 시스템
저널입니다. 매 판단마다 쌓여 608MB 까지 갔고, 지금은 200MB 상한을
걸어 두었습니다(`deploy/fix-service.sh`).

> 운영 서버에서 `data/` 에 쓰는 명령을 **root 로 실행하지 마세요.** 원자적
> 교체(`os.replace`) 때문에 파일 소유자가 root 로 바뀌어 서비스 계정이 못
> 읽게 됩니다. 불가피했다면 곧바로 `bash deploy/fix-perms.sh` 를 돌리세요.
