# 🪙 빗썸 원화 자동매매 콘솔

빗썸 원화마켓 4종(BTC · ETH · SOL · XRP)의 시세 조회, 전략 백테스트,
자동매매 봇. **그 외 기능은 없습니다.**

---

## 설계 원칙

이 프로그램은 이전 버전에서 확인된 문제들을 구조적으로 막도록 다시 만들었습니다.

**1. 봇과 백테스트가 같은 판단 코드를 씁니다**
`services/strategy.py` 의 `decide()` 하나만 존재하고, 실시간 봇과 백테스트가
모두 이것을 호출합니다. 백테스트 결과가 실제 봇의 행동과 일치합니다.

**2. 못 받은 값은 만들지 않습니다**
시세나 캔들을 받지 못하면 추정치를 채우지 않고 그 틱의 판단을 보류합니다.
실시세가 없으면 봇 가동 자체가 거부됩니다.

**3. 주문이 실패하면 내부 장부도 바꾸지 않습니다**
실주문이 거부되면 포지션을 그대로 둡니다. 내부 기록과 거래소 실제 보유량이
어긋나는 것이 가장 위험합니다.

**4. 모든 판단에 근거가 남습니다**
진입·청산마다 어떤 규칙이 왜 발동했는지 로그와 화면에 표시됩니다.

**5. 성과 수치를 지어내지 않습니다**
화면의 모든 숫자는 실제 조회·계산 결과입니다. 홍보용 고정 수치는 없습니다.

## 전략

단순하고 추적 가능한 규칙만 씁니다.

| 구분 | 조건 |
| :--- | :--- |
| **진입** | RSI 가 매수 기준선(기본 35)을 **아래에서 위로** 통과 |
| **청산** | 익절(+4%) / 손절(-2%) / RSI 과매수(70) / 트레일링 스톱(선택) |

RSI 하향 돌파가 아니라 **상향 돌파**로 진입합니다. 하락 중 매수를 피하고
반등을 확인한 뒤 들어갑니다.

> **추세 필터는 기본으로 꺼져 있습니다.** RSI 과매도 반등은 정의상 가격이
> 이동평균 아래일 때 발생하므로, '종가 > 장기MA' 를 함께 요구하면 두 조건이
> 배타적이 되어 진입 신호가 사라집니다. 실측 결과 5종목 × 2간격에서
> 필터 없음 35회 진입 → 필터 적용 시 0~1회였습니다.

## 실행

```bash
git clone https://github.com/jsy15757684/gemini_alpha_lab.git
cd gemini_alpha_lab
cp .env.example .env      # APP_ACCESS_PASSWORD 를 채웁니다
./run.sh
```

`run.sh` 가 가상환경 생성 · 의존성 설치 · `.env` 로드 · 포트 정리까지 처리합니다.
접속은 `http://localhost:8888`.

`APP_ACCESS_PASSWORD` 가 없으면 서버는 뜨지만 **모든 데이터 API 가 503 으로
잠깁니다.** 열린 상태로 떨어지지 않게 의도한 동작입니다.

`.env` 를 수정한 뒤에는 **반드시 서버를 재시작**해야 반영됩니다.

### 환경변수

전체 목록은 [.env.example](.env.example) 참고.

| 변수 | 필수 | 설명 |
| :--- | :--- | :--- |
| `APP_ACCESS_PASSWORD` | ✅ | 접속 비밀번호. 없으면 전체 잠금 |
| `BITHUMB_API_KEY` / `BITHUMB_SECRET_KEY` | | 실계좌 연동. 환경변수로 넣으면 재시작에도 유지 |
| `BITHUMB_PROXY_URL` | | 고정 IP 프록시 경유 (아웃바운드 IP 등록 불가 환경) |

## 측정된 사실 (2026-09-18)

전략을 쓰기 전에 알아야 할 실측 결과입니다. 낙관적인 기본값에 속지 않도록
숫자를 남겨둡니다.

**USDT 환차익** — 차익거래가 아니라 환투자입니다.
137일 실측에서 프리미엄 변동폭은 5.23%p, 환율 변동폭은 16.29% 였습니다.
어떤 매수/매도선 조합으로도 총손익이 음수였고(-0.8%→+1.0%: 왕복 2회 -7.15%),
최악의 거래는 프리미엄이 목표대로 +2.80%p 개선됐는데 환율이 -10.50% 빠져
-7.95% 손실이었습니다. 프리미엄이 +2% 를 넘은 날은 0일이라 기본 매도선으로는
청산되지 않습니다.

주말에는 신호를 쓰지 않습니다. 서울외환시장은 주 5일만 열려서(공시 240일
전부 월~금, 토·일 0건) 토·일에는 금요일 값이 그대로 남는데, 빗썸 USDT 는
24시간 돌아 '역프' 가 깊어 보입니다. 이건 괴리가 아니라 분모가 낡아서
생기는 착시입니다 — 24개 주말을 금 종가→월 종가로 대조하면 USDT -0.242%,
공시환율 -0.222% 로 **프리미엄 자체는 -0.020%p 밖에 안 변합니다.** USDT 가
아직 공시되지 않은 환율 움직임을 먼저 반영하고 있을 뿐입니다. 그 착시를
신호로 받아 매수선(-0.8%)을 통과한 17회를 따라 샀다면 다음 영업일 평균
-0.254% · 승률 12.5% 였고, 일요일 프리미엄의 부호가 월요일 환율 방향을
맞춘 비율은 46% 로 예측력이 없었습니다.
그래서 환율 기준일이 오늘이 아니면 **진입도 익절도 하지 않습니다.**
가격 기준 손절만 계속 작동합니다 — 실제 손실은 공시와 무관하게 쌓입니다.
화면에도 `⏸ 기준 2026-09-18 (1일 전) · 외환시장 휴장` 으로 표시됩니다.

참고로 주말 보유 자체가 불리했습니다: 금→월 28회 중 23회 손실(승률 17.9%,

**무전송 양방향** — 비용을 넘는 괴리가 거의 없습니다.

## 실전 매매 전 확인

- **빗썸은 API 키에 IP 등록이 필수입니다.** `빗썸 계정` 탭에 등록할 IP 가 표시됩니다.
- **유동 IP 회선(집·사무실)은 운영에 부적합합니다.** IP 가 바뀌면 인증이 끊깁니다.
  24시간 운영은 고정 IP 환경에서 하세요.
- **먼저 백테스트, 다음 모의투자, 마지막에 실전** 순서로 확인하세요.
  모의투자(PAPER)는 주문을 내지 않고 같은 전략으로 동작합니다.
- **실전 가동 전 서버가 잔고를 확인합니다.** 인증 실패나 잔고 부족이면 가동을 거부합니다.
- 백테스트는 신호 캔들의 종가 체결·수수료 반영·**슬리피지 미반영** 가정입니다.
  실전 성과는 이보다 나쁠 수 있습니다.

## 점검

```bash
APP_ACCESS_PASSWORD='...' python3 test_system_health.py
```

전략이 설계한 절차대로 도는지 따로 검증합니다 (서버 없이 실행):

```bash
python3 test_strategy_process.py
```

조작한 시장을 주입해 각 분기를 강제로 통과시킵니다. 판단 로직을 테스트가
재구현하지 않고 **실제 봇 루프를 돌립니다** — 재구현하면 '작성자의 이해' 를
검증할 뿐 배포된 코드를 검증하지 못합니다. 실제로 이 방식으로 손절-재매수
루프를 잡아냈습니다.

저장 경로는 임시 디렉터리로 갈아끼워 실행하므로 `data/` 를 건드리지 않습니다.
**이 격리가 없으면 운영 서버에서 실행하는 순간 가동 중인 봇이 사라집니다** —
스크립트가 만든 봇은 `bot_manager` 에 등록되지 않는데 `_persist()` 는 '등록된
봇 전체'(빈 목록)를 저장하기 때문입니다. 실제로 한 번 그렇게 지워졌고 체결
일지로 복원해야 했습니다.

23개 항목을 점검하고, 실패가 있으면 목록과 함께 0 이 아닌 종료 코드를 반환합니다.

상태 파일(`bots.json` · `trades.json` · `arb_bots.json`)의 안전장치는 따로 봅니다:

```bash
python3 test_store_safety.py
```

권한 오류·파손·형식 이상을 일부러 만들어 놓고 **파일이 그대로 남는지**만
확인하는 20개 항목입니다. 이 장치는 2026-09-18 의 사고에서 나왔습니다 —
`data/` 안의 파일이 잠깐 root 소유가 되면서 서비스가 읽지 못했고, 프로그램이
'기록이 없다' 고 믿고 진행한 뒤 다음 저장이 과거를 덮어써 체결 일지 126건이
6건이 됐습니다. 지금은 **읽기 실패와 파일 없음을 구분**하고, 한 번 읽지 못한
파일에는 재시작 전까지 쓰지 않습니다. `bots.json` 에서 같은 일이 나면 봇을
아예 띄우지 않고 화면에 닫을 수 없는 경고를 띄웁니다 — 포지션이 빗썸에
남은 채 감시가 없는 상태를 조용히 넘기지 않기 위해서입니다.

> 운영 서버에서 `data/` 에 쓰는 명령을 **root 로 실행하지 마세요.** 원자적
> 교체(`os.replace`) 때문에 파일 소유자가 root 로 바뀌어 서비스 계정이 못
> 읽게 됩니다. 불가피했다면 곧바로 `bash deploy/fix-perms.sh` 를 돌리세요.
